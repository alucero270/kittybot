M.02 // STM32 TOOLCHAIN ~40 HRS

Bring up the embedded toolchain

Stop being a desktop programmer. Become someone who can flash a microcontroller and watch its UART speak.

Dependencies in
  • Hardware on hand — Nucleo-F446RE, USB cable, multimeter, LED + resistor for blink
  • Month 1 complete — runtime skeleton exists; Logger and Module patterns understood
Milestones
  • Toolchain installed and verified. PlatformIO + VS Code on Windows. CubeMX as a separate generator tool. Empty project compiles and reports the F446RE chip correctly.
  • Blink, the right way. Not Arduino-style. Configure the GPIO peripheral via HAL or LL, with explicit clock setup. Understand why the LED blinks — clock tree, peripheral enable, pin mode, set/reset register.
  • UART echo working. Type characters into a serial terminal on Windows; see them echoed back from the Nucleo. Use printf retargeted to UART for log output. Verify baud rate, parity, stop bits explicitly.
  • Button input with debounce. External button on a GPIO pin. Read it cleanly — debounced, either via timer-based polling or interrupt with software debounce. Now you understand interrupts.
  • First debugger session. Set a breakpoint, step through code, inspect register values. ST-Link-V2-1 over USB, no separate hardware needed.
Acceptance criteria
  • You can flash firmware via pio run -t upload
  • You can open a serial monitor and see your firmware's log output
  • You can set a breakpoint, hit it, and read variable values in the debugger
  • You wrote an ADR explaining HAL vs LL choice for this project
  • You can answer: "What is the clock tree, and why did I have to configure it?"
Risks & how we'll handle them
  • // USB driver issues on Windows
    ST-Link drivers can be flaky on first install. If the Nucleo doesn't enumerate, install ST's ST-Link USB driver manually before troubleshooting code. Half a day max — escalate if longer.
  • // CubeMX-generated code feels alien
    Generated init code is dense. Don't try to read it all at once — focus on what each peripheral's HAL_*_Init does. The reference manual is your friend.
  • // "Blink works, now what" plateau
    Resist Arduino-style "let me just glue tutorials together." Push to UART because that's where real debugging starts.
What you'll learn
CONCEPTMemory-mapped peripherals · clock trees · interrupts vs polling · debouncing · serial protocols · debugger workflow · the difference between "code that compiles" and "code that runs on hardware."
M.03 // FIRST SERVO ~40 HRS

Make a thing in the physical world move

PWM, timer peripherals, and the first real safety lesson — current. Power discipline starts here.

Dependencies in
  • Month 2 complete — UART, GPIO, debugger workflow are familiar
  • Bench setup ready — separate 5V power supply, common ground with Nucleo, multimeter accessible
  • 2× MG90S servos — buy two, expect to burn one
Milestones
  • PWM peripheral configured. Timer in PWM mode, 50 Hz frequency, 1–2 ms pulse width range. Understand: what is the timer counting, and what does the duty cycle physically mean for the servo?
  • Servo sweeps cleanly under firmware control. 0° to 180° and back. Smooth, no jitter, no chatter. The mechanical motion matches the commanded position.
  • Power discipline verified. Servo runs from external 5V supply, not from the Nucleo's 5V pin. Common ground confirmed with multimeter. Current draw measured.
  • Position-from-UART command. Type an angle into the serial terminal; servo moves to that angle. Bare-metal, no host runtime yet — just a parser inside the STM32 firmware.
  • Hardware safety limits in firmware. Reject invalid angles. Implement min/max bounds. Add a "kill" command that snaps to a known safe position.
Acceptance criteria
  • Type 90 in the terminal → servo moves to 90°. Type 0 → moves to 0°. Type 999 → rejected with error log, servo doesn't move.
  • You measured the servo's actual current draw under load with the multimeter
  • You can explain why the servo would brown out the MCU if powered from the Nucleo's 5V pin
  • ADR written: PWM frequency choice, angle-to-pulse mapping, safety limit values
Risks & how we'll handle them
  • // Servo jitters or chatters
    Usually a power issue (insufficient supply, shared ground problem) or PWM frequency mismatch. Multimeter the supply voltage under load, not idle. If it sags below 4.8V, supply is undersized.
  • // Servo dies (you burn one out)
    This is the expected outcome — you bought two on purpose. Common cause: shorting the signal pin to power, or stalling the servo against a hard mechanical limit. Diagnose why before swapping in the spare.
  • // "It moves but I don't understand why"
    Don't accept this. Write the ADR explaining angle-to-pulse mapping. If you can't write it, you don't understand it yet — that's the time to slow down, not push forward.
What you'll learn
CONCEPTTimer peripherals in PWM mode · servo control signaling (1–2ms pulse) · current draw and power discipline · bench measurement workflow · firmware-level safety limits · the gap between commanded and actual position (preview of Month 7's Kalman work).
M.04 // HOST↔STM32 BRIDGE ~40 HRS

Connect the runtime to the hardware

A SerialModule plugs into the Runtime built in Month 1. Everything you build for the next year flows through this protocol.

Dependencies in
  • Month 1 Runtime + Logger + Config — the C++ scaffolding
  • Month 3 servo working — the firmware target
  • Text protocol contract — pulled forward from the v0 prototype's good thinking
Milestones
  • Text protocol specified in an ADR. Format like PTZ <yaw> <pitch>, STATE <name>, newline-delimited. Units are explicit (degrees). Document what happens on malformed input.
  • SerialPort wrapper class on host. Cross-platform serial I/O (libserialport, Boost.Asio, or hand-rolled). RAII over the file descriptor. Non-blocking reads. Errors via std::expected.
  • SerialModule integrated into Runtime. A real kittybot::Module that opens the port on init, reads incoming lines on update, sends outbound commands. This proves the Month 1 architecture works for non-trivial modules.
  • STM32 firmware parses the text protocol. Receives commands, dispatches to servo, sends ack/nack responses. Logs malformed input. The board becomes a well-behaved peripheral, not a free-form REPL.
  • End-to-end demo. Run the host runtime, type PTZ 30 0, watch the servo move to 30°. Both sides log the transaction. ACK comes back. This is your first real distributed system.
Acceptance criteria
  • ./kittybot --config configs/dev.json starts the runtime, opens the serial port, idles cleanly
  • An interactive command (or test harness) sends PTZ 30 0; servo moves; ACK is logged
  • Disconnecting the USB cable mid-session produces a clear error, not a crash. Reconnecting recovers.
  • Tests cover: protocol parsing on the host, protocol formatting on the firmware, malformed-input handling on both sides
  • CI green. README updated with the protocol description and a working demo command.
Risks & how we'll handle them
  • // Serial port permissions / COM enumeration
    Windows COM port numbers shift; the same Nucleo can be COM3 today and COM7 tomorrow. Make the port configurable; auto-detect via VID/PID is a Month-12 polish item, not now.
  • // Buffer / framing bugs
    Newline-delimited text is forgiving but not free. Partial reads are real. Test deliberately: send half a command, wait, send the rest. Your parser should handle it.
  • // Cross-platform serial library churn
    Pick libserialport or Boost.Asio early; don't rewrite mid-month. Document the choice in ADR. We can swap in Month 9 when binary protocol arrives if needed.
  • // Scope creep into "should I make this binary now?"
    No. Text protocol stays through Month 8. Binary in Month 9 is a deliberate decision after you've earned the complexity. Note the ADR explicitly rejects binary for now.
What you'll learn
CONCEPTCross-platform serial I/O · protocol design (framing, units, error responses) · the host↔firmware boundary · graceful failure modes · integration testing across two codebases · the architectural backbone that survives into Month 12.
