// Mission Brief

You haven't written C++ in ten years. Most of that work was Qt, where parent-child trees did your memory management for you. Modern C++ replaces that with RAII — and you got the mental model partly inverted in your last answer. This month corrects it through code, not through textbook exercises.

By the end of Week 4, you have a working C++23 runtime, a structured logger, a config system, and CI. Months 2–4 plug an STM32 module into this Runtime instead of building everything from zero.

W.01

Logger & RAII Fundamentals

~10 HRS
Why this week

A logger owns a file handle. Cleanup at scope exit isn't optional — it's the whole job. RAII reveals itself most clearly through resources that aren't memory: file handles, mutexes, sockets. Every other module written this year will use this logger. There is no throwaway code.

Learning objectives
  • Internalize RAII: resource acquisition is initialization, release is destruction
  • Understand deterministic destructor timing — scope-bound, not GC-bound
  • Use std::unique_ptr and std::lock_guard as RAII tools, not "STL features"
  • Correct the mental model: RAII handles cleanup. The STL is one beneficiary, not the source.
  • Understand exception safety basics — what happens to your file if a throw happens mid-write
Tasks
  • Set up dev environment: g++ 13+ or clang 16+, CMake 3.20+, debugger
  • Implement kittybot::Logger — file output, owned via RAII
  • Add structured fields: timestamp, level, module name, message
  • Make it thread-safe with std::mutex + std::lock_guard
  • Build LogScope RAII helper that logs enter/exit
  • Deliberately throw mid-log inside a LogScope; verify exit still logs
  • Write 3 examples: file-only, stdout-only, both. Use the same Logger class
Deliverable
artifact / A working kittybot::Logger class that opens a file in its constructor, closes in its destructor, is thread-safe, and provides LogScope for timing/scope tracking.
Connection forward
→ Week 2 Runtime uses Logger to log module lifecycle. → Month 4 Serial protocol logs every command sent and ack received. → Month 10 Simulation harness replays from these exact log files.
W.02

Module & Runtime — The Backbone

~10 HRS
Why this week

Ownership flows downward. A Runtime owns its Modules; when the Runtime dies, all Modules die with it. This is the mental model you got inverted last conversation — fix it here, in code, with a system you'll keep using for 15 months.

Learning objectives
  • Abstract base classes and pure virtual functions
  • std::unique_ptr<Module> — what it owns, when it cleans up
  • Move semantics: why unique_ptr is movable but not copyable
  • Polymorphism through owned base pointers; why heap allocation is necessary
  • Lifecycle composition: init → start → update (loop) → stop
Tasks
  • Define abstract kittybot::Module with virtual lifecycle methods
  • Implement kittybot::Runtime holding std::vector<std::unique_ptr<Module>>
  • Write add_module(std::unique_ptr<Module>) using std::move
  • Try to copy a unique_ptr deliberately — read the compiler error, understand it
  • Build HeartbeatModule that logs once per second via the Week 1 Logger
  • Run for 30s, Ctrl-C, verify destructors fire in reverse-add order
  • Answer in your own words: why must Module live on the heap?
Deliverable
artifact / A Runtime that owns modules via unique_ptr, calls their lifecycle in order, and shuts down cleanly. One real HeartbeatModule proves end-to-end.
Connection forward
→ Month 4 Serial protocol becomes a Module. → Month 6 Perception, BehaviorFSM, Control all become Modules. → Month 8 Same Runtime ports to Orin Nano.
W.03

Configuration & Error Handling

~10 HRS
Why this week

Hardcoded values are a smell. Every module needs configuration — serial port, log level, Kalman gains, servo limits. Building this now teaches modern error handling (std::optional, std::expected) and avoids you littering the code with magic numbers all year.

Learning objectives
  • std::optional<T> for "value may be absent" semantics
  • std::expected<T, E> (C++23) for fallible operations — no exceptions
  • Choosing a config format (JSON via nlohmann/json, or TOML via toml++)
  • Designing for sensible defaults vs. required fields
  • Type-safe lookup: config.get<int>("serial.baudrate")
Tasks
  • Choose JSON or TOML; write your first ADR explaining why
  • Add the parser library to CMake (FetchContent or vcpkg)
  • Implement Config::load(path) -> std::expected<Config, ConfigError>
  • Add type-safe get<T> with default value overload
  • Wire log level into Logger from config; observe runtime change
  • Make Runtime read which modules to start from config
  • Test failure modes: missing file, malformed file, missing required field
Deliverable
artifact / A Config that loads from disk, returns clear errors via std::expected, supports defaults, and is wired into Logger and Runtime.
Connection forward
→ Month 7 Kalman tuning constants live in config. → Month 11 Servo limits and trajectory parameters in config. → Always Tuning without recompiling.

Cross-cutting discipline

No raw new / delete
If you type new, it's wrapped in a smart pointer immediately. If you type delete, you're doing something wrong. There are exceptions, but you shouldn't hit one in Month 1.
Owners are obvious
For every resource — memory, file, mutex, socket — one place owns it. That place is responsible for cleanup. If you can't point to the owner in five seconds, the design is wrong.
Commit small, commit often
A commit per task is fine. Build commit message hygiene from day one. feat(logger): add LogScope helper beats updates.
Read the compiler error
Modern C++ compiler errors are dense but precise. Read them line by line. The error you ignore in Week 1 is the one you don't understand in Month 7. The "try to copy unique_ptr" exercise is deliberately there to make you read one.
Document decisions, not code
Code comments explain why, not what. ADRs capture trade-offs that aren't obvious from the code. Both compound in value.
